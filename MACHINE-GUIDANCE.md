# Machine-aware workout guidance

Workout definitions use normalized `activities` values (`bike`, `elliptical`, or `strength`). Allowed activities belong to the workout definition. The active activity belongs to the workout session.

A workout with exactly one allowed activity resolves that activity automatically when the session starts. A workout with more than one allowed activity does not start until the user explicitly chooses one of the allowed activities. Cancel and Restart currently clear session state, so the next Start requires a new choice. Pause, resume, and reloading an in-progress session keep the stored session activity. The choice is not a profile or equipment preference and does not alter `data.json`.

Equipment selection is stored separately from the physiological profile under the local-storage key `sisu_trainer_equipment_selection`. The current shape is:

```json
{
  "bike": "proform-smart-power-10"
}
```

The machine registry currently contains only ProForm SMART Power 10.0 profile version 1. Its resistance-to-watts table is an empirical approximation measured near 70 RPM, not manufacturer watt data. Automatic guidance is limited to resistance 1–15. Working guidance targets 70 RPM; recovery uses 63 RPM and omits estimated watts.

Machine policy is isolated in `src/machines/proformSmartPower10.ts`. Heart-rate adaptation uses a rolling median and requires at least five distinct valid samples spanning at least four seconds. Short work intervals (≤75s) adapt the next repetition only; if the final in-phase tick is missed, the runtime finalizes from the completed work window at the phase boundary without speaking or tracing the internal next-resistance decision. The generic runtime maintains a bounded 15-second HR buffer, transient controller state, duplicate-free voice events, and a trace that appends only when the active recommendation’s resistance, cadence, or estimated watts changes. Transient state resets when a workout starts or restarts.

Local workout summaries can include `activity`, `machine_id`, `machine_profile_version`, and `machine_guidance_trace`. This repository contains no SISU server schema or evidence that `/workout/ingest` accepts arbitrary summary fields. The SISU client therefore removes those local-only fields before sending the existing network payload.

Learned starting resistance is a local historical personalization of work-phase starts. It is keyed by machine, machine profile version, activity, workout intent, and work-duration class (`short` ≤75s, `medium` 76–150s, `long` >150s), not by weekday. The existing ProForm defaults remain the fallback when no trustworthy learned value exists. Learning uses only qualifying completed bike sessions on the current machine profile; cancelled workouts and sessions without a plausible late-work heart-rate response do not train it. Heart-rate qualification uses the ending response of each selected work interval (final 15s short, final 30s medium, final third long), each against that interval’s own target ±3 bpm, not the whole-rep median or a combined target range. The first qualifying session stores the derived candidate directly; later updates move by at most one resistance level. Learned resistance only initializes the first applicable work recommendation. After that, the existing HR-adaptive controller remains authoritative. Learned state can be reset from Settings → Equipment without deleting workout history.

HR-response dynamics are a separate local observation model. They measure how long heart rate usually takes to move after a work start or a ±1 resistance change, and how much it usually changes, using completed qualifying ProForm bike workouts. Work-start responses are distinct from in-work resistance-step responses; a recovery-to-work jump is never treated as a large mechanical dose. Response delay uses a persistent rolling-median movement of at least 3 bpm for three consecutive seconds, not a single sample. Each observation is truncated by the next resistance change, the work-phase end, or 90 seconds. Compact aggregates keep the last 20 qualifying values per metric and expose medians. Reliability is stored separately from those delay arrays: each kind tracks how many response windows were genuinely observable and how many of those produced a detected onset. An observation opportunity requires a usable baseline, a window of at least 15 seconds, and enough valid post-event HR to have evaluated a three-consecutive-second onset run; scattered coverage and dropout HR are not counted as physiological non-response. Lifetime counts remain diagnostic. The last 20 observable opportunities per kind are stored as a delay or null so recent detection rate, delay median, MAD, and concentration share one population; missing recent arrays sanitize to empty and are never backfilled from delay arrays. Keys match learned starts (machine, profile version, activity, intent, duration class) and are not migrated across profile versions. Users can reset HR-response data independently of learned starting resistance. Raw workout history is not modified. These observations are not medically validated.

Trusted delay observations can conservatively extend medium and long evaluation timing. Later-only timing still uses the detected-delay arrays and requires at least five delay samples with a median absolute deviation of at most 10 seconds. High-confidence earlier timing uses only the bounded recent opportunity population and requires at least 10 recent detected responses, a recent detection rate of at least 80%, MAD of at most 5 seconds, and at least 70% of detected delays within the median ±10 seconds. Lifetime counts and legacy delay-array lengths do not grant earlier timing; older stores must accumulate new recent opportunities. When recent evidence earns that gate, medium evaluation may occur as early as 45 seconds (`median + 15`, never below 45), long first evaluation as early as 60 seconds (`median + 20`, never below 60), and long directional cooldowns as early as 45 seconds (`median + 15`, never below 45). If the recent candidate is not earlier than the original default, the existing later-only result is kept. Short intervals remain full-repetition only. HOLD evaluations keep a 60-second cooldown. Heart-rate adaptation thresholds (±3 bpm, R13+ 5 bpm deficit) are unchanged. Per-level HR-delta measurements remain diagnostic only. Personalized timing is derived from the current dynamics store when a work phase begins and is frozen for that phase, so resetting HR-response data restores default timing on the next session or work phase without a separate timing store. Learned starting resistance remains independent.

Resistance-dose prediction is currently shadow-only. It never changes resistance, evaluation timing, HR thresholds, cadence, voice, workout instructions, trace semantics, or SISU payloads. It uses historical directional HR-per-level response from the existing dynamics store (`increaseHrPerLevel` and `decreaseHrPerLevel`); increase and decrease are modeled independently and are never combined into one absolute HR-per-resistance metric. A shadow estimate requires at least five usable directional samples, a median absolute deviation of at most 5 bpm, at least 70% sign consistency in the expected direction, and a median with the expected sign. The model predicts both the expected HR response to the controller’s actual ±1 (or legacy ±2) step and a capped hypothetical resistance needed to reach the nearest target boundary. The hypothetical suggestion is diagnostic only and is capped at ±3 levels, then clipped to R1–R15; predicted HR for that suggestion uses the physically achievable step count, which may be smaller than the capped request. The live controller remains ±1. Realized HR response is compared with the one-step prediction, not the counterfactual multi-level suggestion. Prediction events and errors are stored locally under `sisu_trainer_shadow_resistance_predictions`, bounded to the newest 20 events per key per direction, and can be reset independently of learned starts and HR-response data. Predictions for a workout use only dynamics learned before that workout; the current workout never trains its own predictor. A session is shadow-evaluated at most once, including when that first evaluation produced no prediction. A compact processed-session ledger in the local shadow store preserves that outcome even after diagnostic events fall out of the 20-event window. Loading an older store without that ledger backfills it from session IDs on the stored prediction events; sessions that originally produced no prediction cannot be recovered. Completing the same workout again does not append, replace, or newly create a prediction with a later model.

Shadow validation judges those frozen actual-step predictions and never reruns them with the current dynamics model. High-confidence validation uses only actual ±1 events; stored ±2 observations remain diagnostic history and do not grant ±1 confidence. Increase and decrease are validated independently. Events with a prediction but no observed HR delta remain in the realization-rate denominator. High confidence requires at least 10 realized ±1 predictions, at least 5 distinct sessions, a realization rate of at least 80%, median absolute error of at most 3 bpm, absolute median signed bias of at most 2 bpm, direction match of at least 80%, and at least 80% of realized predictions within 5 bpm. Missing session IDs cannot establish high confidence. Validation does not authorize predictive resistance control, does not change timing, voice, workout UI, trace, or SISU, and is not medically validated. Resetting shadow prediction data removes validation evidence because metrics are derived from the bounded events; the processed-session ledger is kept.

A local machine-learning diagnostics snapshot can be exported from Settings → Equipment. It is user-initiated, stays on the device, and does not change resistance, timing, voice, workout UI, trace, or SISU. The snapshot summarizes selected machine identity, learned starting resistance, HR-response dynamics, timing evidence and defaults, shadow prediction, validation status, and progress toward the existing validation gates. It does not invent a phase duration in order to state a concrete evaluation time. It reports how many sessions have already been shadow-processed, but omits processed-session IDs and raw HR. There is no automatic upload or network call. This export exists so real-workout evidence can be inspected before any future increase in controller authority.

Current development checkpoint: the adaptive measurement, prediction, and validation infrastructure is built. The current product phase is evidence collection from real workouts. A later controller-authority phase should not begin merely because the code can support it; it should begin only after real shadow validation evidence has been reviewed.
